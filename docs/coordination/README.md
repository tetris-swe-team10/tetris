# 제안·요청·질문으로 협업하기

> 상태: 사용자 도입 승인 · 2026-11-16 · A/Codex. 팀원 의견은 P-A-001에서 수집한다.

EndPoint [협업 방식](https://github.com/2026ENDPoinT/team19/blob/main/docs/08-collaboration.md)의 ‘저장소에 남겨 다른 역할의 AI가 읽기’를 참고했다.
이 프로젝트는 소공 평가에 맞게 **이슈·PR·동료 리뷰를 유지**한다. 참고 저장소의 PR 없는 병합·main 직접 작업·특정 팀장 전용 권한은 가져오지 않는다.

| 목적 | 파일·ID | 상태 흐름 |
| --- | --- | --- |
| 공용 계약·규칙·다른 역할에 영향을 주는 변경 제안 | `proposals/P-A-001.md`처럼 역할별 번호 | 초안 → 의견 수집 → 승인/보류/철회 → 반영 |
| 특정 역할에게 리뷰·구현·연동을 부탁 | `requests/R-A-001.md`처럼 역할별 번호 | 작성 → 전달 → 확인 → 진행 → 완료/보류 |
| 답변이나 해석이 필요 | [questions.md](questions.md)에 `Q-A-001` 등 추가 | 열림 → 답변됨 → 결정 필요/종료 |
| 실제 승인된 결정 | [decisions.md](decisions.md)의 D-번호 | 승인자·날짜·근거와 함께 기록 |

## 작성과 답변 규칙

- 제안·요청은 한 건에 한 파일. ID는 작성 역할의 마지막 번호 다음을 사용한다. 기존 Q-001~Q-004는 유지한다.
- `작성자: A/Codex`, `받는 역할: B,C`, `상태`, `요구사항/Issue/PR`, `답변 위치`, `완료 조건`을 적는다. 모르는 기한을 임의로 만들지 않는다.
- 요청서는 ‘내 코드 리뷰 부탁’과 ‘상대가 구현해야 할 새 기능’을 구분한다. 요청 등록만으로 상대의 일정·담당을 바꾸지 않는다.
- 상대 역할 의견 칸은 비워 둔다. 당사자가 자기 의견·답변·확인 근거를 추가한다. 요청자는 요약하더라도 원문 링크를 남긴다.
- 공통 질문은 맨 아래 추가한다. 기존 질문 내용은 보존하고 답·상태·근거를 덧붙인다. 끝난 항목은 이력 링크를 남기고 보관할 수 있다.
- 팀에 영향을 주는 미승인 변경은 먼저 제안한다. 이미 사용자가 승인한 구현은 진행하고, 제안 때문에 다시 승인을 요구하지 않는다.

## 전달과 리뷰·병합

1. 작성한 파일을 작업 브랜치에 push하고 PR에서 **그 브랜치의 요청서 링크**를 공유한다. main에 아직 없는 파일은 main 링크를 쓰지 않는다.
2. GitHub 리뷰 요청과 PR 코멘트의 실제 수신자를 확인한다. 문서 저장·GitHub 전달·상대 확인은 각각 구분한다.
3. 팀원은 PR에 코드 위치·조건·영향 또는 검토 범위와 결과를 한국어로 남긴다. 문제를 찾지 못했다면 억지 지적을 만들지 않는다.
4. 작성자는 수정/미수정 이유와 관련 검증·커밋을 답글로 남긴다. 요청 완료는 실제 응답·연동 근거가 있을 때만 표시한다.
5. **이번 A PR은 다른 사람의 실질적인 리뷰 코멘트가 달리고 차단 지적을 해결한 뒤 병합한다.** 인사·이모지·작성자 자체 리뷰는 조건을 충족하지 않는다. 최신 HEAD·충돌·필수 체크도 확인한다. 자동 병합은 켜지 않는다.

이 조건은 사용자의 2026-11-16 지시다. 단순 코멘트가 달렸다는 이유로 미해결 버그가 있는 코드를 병합하지 않는다.
시작 루틴은 내 역할 앞으로 온 열린 항목만 읽고, 종료 루틴은 실제 상태와 PR 답변 링크를 갱신한다.

## 양식

제안은 [제안 양식](proposals/TEMPLATE.md), 요청은 [요청 양식](requests/TEMPLATE.md)을 복사한다.
질문은 기존 질문 목록에 아래 형식으로 추가한다.

```text
ID: Q-A-다음번호 / 상태: 열림 / 작성: A/도구 / 받는 역할: B
질문과 필요한 이유:
선택지·추천(있으면):
관련 요구사항·Issue·PR:
답변(수신자가 작성):
결정·완료 근거:
```
