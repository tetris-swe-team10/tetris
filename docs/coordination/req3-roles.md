# 3차 요구사항(대전 모드) 역할 분담

> 상태: 팀 합의 · 정리일: 2026-11-15 · 출처: 교수님 「Requirements 3」 PDF, 팀 노션 「3차 요구사항 역할 분담」
> 인터페이스: PR #56 (`game/versus`, `ui/BoardRenderer`, `net`). 구현 상태는 각 이슈·PR에서 확인한다.

## 역할

| 역할 | 담당 | 1주차 | 2주차 | 평가 대비 |
| --- | --- | --- | --- | --- |
| A 같은 PC 대전 | 혜원 | 대전 규칙 엔진 | 같은 PC 대전 화면, 2인 키 | 2차 아이템 요구사항 명세서 |
| B 리팩토링 → P2P 대기실까지 | 수연 | 현재 커버리지 측정, 리팩토링 | 소켓 연결, 랙·끊김 판정, 대기실 화면 | 커버리지 측정·공유 |
| C 디자인 → P2P 게임 중 | 서현 | 전체 화면 디자인 | 게임 중 데이터 송수신, P2P 게임 화면 | 1·2차 요구사항 재점검 |

- 각 주차 안에서는 세 역할이 병렬로 진행한다. 1주차 끝까지 리팩토링과 디자인을 완료한다.
- P2P는 '게임 시작'을 기준으로 앞(연결·대기실)은 B, 뒤(게임 중·승패·복귀)는 C가 맡는다.
- 테스트는 각자 자기 코드에 작성한다. 커버리지 70%는 공동 책임이며 B가 측정해 부족한 영역을 담당자에게 알린다.

## 담당 코드 범위

| 역할 | 구현하는 곳 | 사용만 하는 곳 |
| --- | --- | --- |
| A | `game/versus/*`(`VersusMatch` 구현 포함), `GameEngine`의 공격 진입점, `GameSnapshot`의 `garbageCells`·`pendingAttack` 채우기, 같은 PC 대전 화면·2인 키 설정 | `BoardRenderer` |
| B | `GameView` 리팩토링, `BoardRenderer` 구현, `ConnectionChannel` 구현, 연결·대기실 `NetMessage`, P2P 메뉴·대기실 화면, 최근 IP 저장 | `P2pGameLauncher`(호출) |
| C | 디자인 목업·화면 명세, `P2pGameLauncher` 구현, 게임 중 `NetMessage`(스냅샷·공격 줄·종료), P2P 게임 화면 | `ConnectionChannel`, `BoardRenderer`, `GameEngine.receiveAttack` |

- 인터페이스를 바꿔야 하면 사용하는 역할에게 먼저 알리고 같은 PR에서 함께 수정한다.
- 상대 구현이 끝나기 전에는 가짜 구현으로 개발한다 (예: C는 가짜 `ConnectionChannel`).
- 상대 보드 전송: `BoardStateMessage`에 `GameSnapshot`을 변환 없이 담고 받는 쪽은 그대로 `BoardRenderer`에 넘긴다. 공격 줄은 `AttackMessage`. 스냅샷에 새 필드를 넣을 때는 직렬화 가능한 값만 쓴다.
- 대기실 → 게임 전환: B는 시작 메시지를 처리하는 핸들러 안에서 `P2pGameLauncher.start`를 동기 호출하고, C는 `start`가 끝나기 전에 게임 핸들러를 설치한다. 채널은 메시지를 도착 순서대로 하나씩 전달한다 (`ConnectionChannel` 주석, `P2pContractTest`).
- 테스트용 가짜 채널: `app/src/test/.../net/FakeConnectionChannel`

## 맞춰야 하는 시점

1. 1주차 시작: PR #56 확인·병합, 현재 커버리지 공유
2. 1주차 끝: 리팩토링 PR 병합(A 리뷰), 디자인 공유
3. 2주차 마무리: B·C 실제 연결 통합, 두 PC 실측, 전체 테스트, 커버리지 70% 확인
