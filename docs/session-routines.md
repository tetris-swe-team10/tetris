# 시작 루틴과 종료 루틴

> 적용일: 2026-11-09 · 대상: 이 저장소에서 작업하는 사람과 AI · 상세 정책은 [AI 지침](ai-guide.md)을 따른다.

사용자가 **“시작 루틴 해줘”**, **“동기화하고 이어서 하자”**라고 하면 시작 루틴을 실행한다. 새 세션의 첫 작업에서도 같은 확인을 짧게 수행한다.
**“종료 루틴 해줘”**, **“오늘 작업 정리해줘”**라고 하면 종료 루틴을 실행한다. 단순 문서 읽기나 질문 답변을 별도 구현 작업으로 부풀리지 않는다.

## 시작 루틴

### 1. 저장소와 로컬 변경 확인

```powershell
git branch --show-current
git status --short
git log -1 --oneline
```

- 현재 브랜치와 기준 커밋을 확인한다. 변경 파일은 작업에 해당하는 범위만 diff를 읽는다.
- 이전 사람/도구가 남긴 수정, IDE 산출물, 진행 중 merge·rebase·cherry-pick을 확인한다. 작업 중인 파일을 되돌리거나 삭제하지 않는다.
- 개인 이름·역할이 이미 대화·이슈에 있으면 다시 묻지 않는다. 문서 작성자와 실제 작업 담당자는 구분한다.

### 2. 원격과 안전하게 동기화

- 네트워크 접근이 가능하면 `git fetch origin`으로 원격 정보를 갱신한다. fetch는 로컬 파일을 덮어쓰지 않는다.
- 현재 브랜치의 upstream과 `origin/main` 대비 차이, 선행 PR을 확인한다. 관련 이슈·PR에 새 댓글이나 변경된 HEAD가 있으면 읽는다.
- clean 상태인 main이 원격보다 뒤에 있고 fast-forward만 필요하면 `git pull --ff-only origin main`으로 갱신할 수 있다.
- dirty 상태, 분기된 이력, 진행 중 충돌에서는 자동 pull·stash·reset·강제 push를 하지 않는다. fetch한 기준과 필요한 후속 조치를 알린다.
- 기능 브랜치의 동기화는 그 작업의 필요와 승인 범위에 따라 별도로 진행한다. 시작 루틴만으로 main을 기능 브랜치에 임의 merge하지 않는다.
- 네트워크/인증이 실패하면 같은 요청을 오래 반복하지 않는다. 로컬 기준과 원격 미확인을 표시하고 독립적으로 할 수 있는 일을 계속한다.

### 3. 인수인계와 결정 읽기

`read.md`와 [협업 안내](coordination/README.md)를 읽고 `requests/`에서 내 역할 앞으로 온 미완료 요청, `proposals/`의 내 의견이 필요한 항목, `questions.md`의 열린 질문을 확인한다. 아직 main에 없는 요청은 해당 PR 브랜치에서 읽는다.

대전 작업은 먼저 [역할별 시작점](tasks/README.md)에서 지정된 A/B/C 문서를 읽는다. 사용자가 “A파트”라고 지정하면 배정표의 A 범위를 이어간다.

1. [작업 현황](coordination/status.md)의 다음 작업·막힌 점·관련 이슈/PR.
2. [결정 기록](coordination/decisions.md)의 해당 작업 관련 변경과 [열린 질문](coordination/questions.md).
3. 작업할 기능 명세와 필요한 코드·테스트. [문서 지도](README.md)에서 찾는다.

노션 원문 전체와 모든 테스트 보고서를 매번 읽지 않는다. 이미 끝난 이슈를 새 작업으로 중복 등록하지 않고, 오래된 체크박스·커버리지 숫자를 현재 결과로 인용하지 않는다.

### 4. 짧게 보고하고 진행

```text
브랜치/기준: …
동기화: 최신 확인 / 로컬 기준(원격 미확인) / 충돌·분기 확인 필요
로컬 변경: 이번 작업 / 보존할 다른 변경
이어갈 작업: 요구사항·Issue·PR 및 현재 상태
새 결정·열린 질문: 해당 항목만
검증 계획: 직접 관련된 테스트 또는 문서 확인
```

사용자가 이미 할 일을 지정했으면 보고 후 그 작업을 진행한다. 시작 루틴만 요청했고 이어갈 목표가 없으면 우선순위가 높은 다음 작업을 1~3개 제안한다. 임의로 새 기능·담당자·일정을 확정하지 않는다.

## 종료 루틴

### 1. 실제 변경과 검증 결과 정리

- `git status --short`와 이번 작업의 diff를 확인하고, 완료한 내용·미완료·실패·미실행을 구분한다.
- 해당 변경에 필요한 검증이 아직 없으면 관련 테스트만 고른다. 이미 통과했고 이후 변경하지 않은 검증은 반복하지 않는다.
- 문서 변경은 링크·경로·출처·원문 보존을 확인한다. 종료 루틴이라는 이유만으로 전체 테스트나 커버리지를 실행하지 않는다.
- 원본 아카이브의 공백·문법을 새 문서 스타일에 맞추어 수정하지 않는다. 새 문서와 변경 코드만 `git diff --check` 대상으로 삼는다.

### 2. 다음 작업자가 이어갈 기록 남기기

- [작업 현황](coordination/status.md)에 이번 작업과 다음 행동을 짧게 추가한다. 오래된 날짜의 현황을 오늘 검증한 것처럼 일괄 갱신하지 않는다.
- 새 합의가 실제 있었으면 [결정 기록](coordination/decisions.md)에 근거를 추가한다. 답이 없는 사항은 [열린 질문](coordination/questions.md)에 남긴다.
- 새로 결정하거나 달라진 내용이 없으면 해당 파일을 형식적으로 수정하지 않는다. 상세 내용은 실제 이슈·PR·기능 명세로 연결한다.

```text
작업/담당/날짜:
기준 브랜치·커밋:
완료한 변경:
관련 Issue·PR·반영 커밋:
검증 명령·범위·결과 또는 미실행 이유:
남은 작업·막힌 점:
새 결정·질문 ID:
다음 사람이 먼저 할 일:
게시 상태: 로컬 수정 / 커밋 / push / PR / main 병합 / 릴리스
```

### 3. 승인된 범위로 저장·공유

| 요청·기존 승인 | 수행 범위 |
| --- | --- |
| “종료 루틴”, “작업 정리”만 요청 | 로컬 기록과 상태 보고. 원격 작업이 이미 승인돼 있다면 그 범위까지 진행 |
| “종료 루틴하고 커밋·push” | 이번 작업 파일만 명시해서 stage → diff 확인 → 커밋 → 현재 작업 브랜치 push |
| “PR까지 올려줘” | 기존 PR 확인 후 재사용하거나 생성. 실제 검증과 남은 범위를 기록 |
| “main에 병합해줘” | PR 대상·HEAD·의존 관계·실제 포함 변경을 확인한 뒤 병합하고 로컬 main 갱신 |

이미 받은 승인을 반복해서 묻지 않는다. 단순한 종료 요청을 승인되지 않은 main 병합·새 릴리스 발행·팀원 메시지 전송으로 확대하지 않는다.
push 전에 원격 변경을 확인하고, 예기치 않은 선행 기능 커밋이 섞이면 범위를 정리한다. 충돌 해결이 실제 동작을 바꾸면 직접 영향받는 검증만 추가한다.

### 4. 마지막 보고

**한 일 / 실제 검증 / 남은 일 / 현재 브랜치 / 커밋·PR·병합 여부**를 짧게 전달한다. 승인된 게시 작업이 실패했다면 로컬 저장 상태와 실패 이유를 적는다. 인증 정보나 개인 경로의 민감한 값은 문서·로그에 남기지 않는다.

## 자주 쓰는 요청 문장

- `시작 루틴 해줘. 진행 중인 PR부터 확인하자.`
- `시작 루틴 하고 이슈 #번호 이어서 구현해줘.`
- `종료 루틴 해줘. 오늘 한 일과 다음 할 일만 정리해줘.`
- `종료 루틴 하고 이번 변경만 커밋·push해줘.`
- `종료 루틴 하고 PR까지 올려줘. 테스트는 관련된 것만 해줘.`
