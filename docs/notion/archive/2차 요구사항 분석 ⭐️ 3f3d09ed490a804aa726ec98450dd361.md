# 2차 요구사항 분석서

## 0. 문서 목적과 분석 기준

이 문서는 교수님이 제시한 2차 요구사항을 페이지별로 분석하고, 사용자에게 필요한 기능과 개발·검증에 필요한 상세 조건을 연결한다.

아직 결정되지 않은 사항은 확정된 요구사항처럼 작성하지 않는다. 현재 코드에 구현되어 있다는 이유만으로 해당 동작을 요구사항으로 확정하지 않는다.

### 0.1 이해관계자

| 이해관계자 | 관심 사항 |
| --- | --- |
| 교수님 | 과제 요구사항 충족, 설계·검증·협업 과정 |
| 게임 사용자 | 난이도 선택, 예측 가능한 게임 규칙, 아이템 식별과 조작 |
| 개발팀 | 구현 범위, 경계 조건, 기능 간 연동, 변경 영향 |
| 평가팀 | 명세에 따른 재현 가능한 평가 방법과 기대 결과 |

### 0.2 요구사항 분류

| 분류 기준 | 구분 | 의미 |
| --- | --- | --- |
| 상세 수준 | 사용자 요구사항 | 사용자가 무엇을 할 수 있어야 하는지 자연어로 설명 |
| 상세 수준 | 시스템 요구사항 | 입력·조건·동작·결과·예외를 구체적으로 명시 |
| 성격 | 기능 요구사항 | 시스템이 제공하거나 금지해야 하는 동작 |
| 성격 | 비기능 요구사항 | 사용성·확장성·호환성 등 품질 및 제약 |
| 성격 | 프로젝트·검증 제약 | 도구 사용, 이슈 관리, 테스트, 제출 기준 |

예를 들어 “아이템을 쉽게 구분할 수 있어야 한다”는 사용성 목표이며, “아이템마다 서로 다른 문자를 표시해야 한다”는 그 목표를 지원하는 기능 요구사항이다.

### 0.3 출처와 결정 상태

두 속성을 별도로 관리한다.

| 속성 | 값 | 의미 |
| --- | --- | --- |
| 출처 | 원문 | 교수님 문서에 직접 제시 |
| 출처 | 도출 | 원문을 충족하기 위해 분석 과정에서 구체화 |
| 출처 | 팀 추가 | 팀이 제안한 기능이나 규칙 |
| 결정 상태 | 확정 | 원문으로 명확하거나 합의 완료 |
| 결정 상태 | 제안 | 팀 검토·합의 필요 |
| 결정 상태 | 확인 필요 | 교수님 또는 이해관계자 확인 필요 |

예를 들어 “오차 ±5%”는 **출처는 원문이지만 계산 기준은 확인 필요**인 요구사항이다.

요구사항 ID는 `R2-페이지-번호`로 작성한다. 검증 항목에도 같은 ID를 연결한다.

## 1쪽. Requirements 2

### 원문 분석

2차 요구사항 문서의 표지다. 이 페이지에는 별도의 구현 요구사항이 없다.

### 문서 관리

- 이 분석서는 2차 요구사항을 대상으로 한다.
- 1차 요구사항을 대체하지 않고 추가·변경 사항을 정리한다.
- 1차 요구사항과의 충돌 여부는 원문 대조 후 판단한다.

## 2쪽. 아이템 모드 개발

### 교수님이 제시한 내용

- 아이템 모드를 추가하고 일반 모드를 일부 수정한다.
- 직접 제시되지 않았더라도 요구사항 충족에 필요한 수정 사항을 찾아 처리한다.
- 비기능 요구사항도 구현과 테스트에서 고려한다.
- 명시되지 않은 부분은 요구사항에 어긋나지 않는 범위에서 자유롭게 구현할 수 있다.

### 사용자 요구사항

사용자는 기존 일반 게임과 새 아이템 게임을 이용할 수 있어야 한다. 새 기능이 추가되어도 기존에 제공하던 기능을 정상적으로 사용할 수 있어야 한다.

### 상세 요구사항

| ID | 요구사항 | 성격 | 출처 |
| --- | --- | --- | --- |
| R2-02-01 | 일반 모드의 변경 사항과 아이템 모드 추가 사항을 모두 제공해야 한다. | 기능 | 원문 |
| R2-02-02 | 새 기능은 유지되어야 하는 1차 요구사항과 충돌하지 않아야 한다. | 호환성 | 도출, 10쪽 연계 |
| R2-02-03 | 원문에 없는 세부 규칙은 팀 결정 사항으로 기록해야 한다. | 관리 | 도출, 12쪽 연계 |

### 검증 기준

- 일반 모드와 아이템 모드 각각의 실행 경로를 확인한다.
- 1차 요구사항별 회귀 검증 목록을 작성한다.
- 팀이 추가한 규칙이 원문 요구사항을 무효화하지 않는지 검토한다.

### 분석 시 주의

“높은 품질”만으로는 합격 여부를 판단할 수 없다. 이후 페이지에서 사용성·확장성·테스트 기준 등으로 구체화해야 한다.

## 3쪽. 기존 방식의 변경사항

### 교수님이 제시한 내용

일반 모드에 난이도 설정을 추가한다. 난이도에 따라 I형 블록의 등장 빈도와 줄 삭제에 따른 낙하 속도 증가량이 달라져야 한다. 스코어보드에 난이도를 구분하고, 줄 삭제 애니메이션을 추가한다.

### 사용자 요구사항

- 사용자는 Easy·Normal·Hard 중 원하는 난이도를 선택할 수 있어야 한다.
- 사용자는 어떤 난이도에서 얻은 점수인지 확인할 수 있어야 한다.
- 사용자는 어떤 줄이 삭제되는지 알아볼 수 있어야 한다.

### 상세 요구사항

| ID | 요구사항 | 성격 | 출처·상태 |
| --- | --- | --- | --- |
| R2-03-01 | 일반 모드의 설정에서 Easy·Normal·Hard를 선택할 수 있어야 한다. | 기능 | 원문 |
| R2-03-02 | Easy에서는 I형 블록의 생성 가중치를 기준 대비 20% 높여야 한다. | 기능 | 원문, 4쪽으로 해석 보완 |
| R2-03-03 | Hard에서는 I형 블록의 생성 가중치를 기준 대비 20% 낮춰야 한다. | 기능 | 원문, 4쪽 연계 |
| R2-03-04 | 줄 삭제에 따른 속도 증가량은 Easy에서 기준보다 20% 작아야 한다. | 기능 | 원문, 계산식 확인 필요 |
| R2-03-05 | 줄 삭제에 따른 속도 증가량은 Hard에서 기준보다 20% 커야 한다. | 기능 | 원문, 계산식 확인 필요 |
| R2-03-06 | 스코어보드에서 기록을 획득한 난이도를 식별할 수 있어야 한다. | 기능 | 원문 |
| R2-03-07 | 삭제 대상 줄을 구분할 수 있는 애니메이션을 제공해야 한다. | 기능·사용성 | 원문 |

### 개발자가 구체화해야 할 조건

- **초기 낙하 속도**와 **줄 삭제 후 속도 변화량**을 구분한다.
- 기록에 표시할 난이도는 기록을 획득한 게임의 난이도여야 한다.
- 현재 설정을 변경했다고 과거 기록의 난이도가 달라져서는 안 된다.
- 삭제 연출이 점수·줄 삭제를 중복으로 발생시키지 않아야 한다.

위 조건 중 기록 보존과 중복 방지는 원문을 충족하기 위해 도출한 조건이다.

### 검증 기준

- 세 난이도를 각각 선택하고 실제 게임에 반영되는지 확인한다.
- 같은 줄 삭제 조건에서 난이도별 속도 변화량을 비교한다. **합격 수치는 계산식 확정 후 작성한다.**
- 서로 다른 난이도의 기록을 저장한 후 구분해서 표시되는지 확인한다.
- 한 줄과 여러 줄 삭제에서 대상 줄이 표시되는지 확인한다.

### 확인·결정 필요

1. “속도 증가”는 초당 이동 속도의 증가인가, 낙하 간격의 감소인가?
2. 속도가 증가하는 줄 수 단위와 최대 속도는 무엇인가?
3. 게임 중 난이도 변경을 허용하는가?
4. 아이템 모드에도 동일한 난이도를 적용하는가?
5. 애니메이션 시간과 연출 중 입력 처리 방식은 무엇인가?

**흰색 반짝임은 예시이며 필수 표현 방식이 아니다.** 난이도별 추가 점수 규칙도 팀이 선택할 수 있는 사항이다.

## 4쪽. 확률에 따른 블록 생성

### 교수님이 제시한 내용

블록별 생성 확률을 다르게 처리해야 한다. 다른 블록의 가중치가 10이면 Easy의 I형 블록은 12를 갖는다. 구현 방법으로 Roulette Wheel Selection을 제시한다.

### 사용자 요구사항

사용자는 선택한 난이도에 따라 I형 블록의 등장 빈도가 달라지는 게임을 이용할 수 있어야 한다.

### 상세 요구사항

| ID | 요구사항 | 출처 |
| --- | --- | --- |
| R2-04-01 | 블록 생성 결과는 각 블록에 설정된 가중치를 반영해야 한다. | 원문 |
| R2-04-02 | 블록의 기대 선택 확률은 해당 가중치를 전체 가중치 합으로 나눈 값으로 계산한다. | 도출 |
| R2-04-03 | 실제 게임에서 사용하는 생성 기능이 난이도별 가중치를 적용해야 한다. | 원문, 5쪽 연계 |

7종의 블록과 다른 블록의 가중치 10을 전제로 계산하면 다음과 같다.

| 난이도 | I형 가중치 | 다른 각 블록 가중치 | I형 기대 확률 |
| --- | --- | --- | --- |
| Easy | 12 | 10 | 12/72 ≈ 16.67% |
| Normal | 10 | 10 | 10/70 ≈ 14.29% |
| Hard | 8 | 10 | 8/68 ≈ 11.76% |

### 검증 기준

- 가중치 합과 블록별 기대 확률을 확인한다.
- 난이도 변경 시 적용되는 가중치를 확인한다.
- 실제 선택 결과의 분포는 5쪽의 테스트 기준으로 확인한다.

### 요구사항과 설계의 구분

- **요구사항:** 가중치에 따라 블록이 생성되어야 한다.
- **설계 방법:** Roulette Wheel Selection으로 구현한다.

원문은 해당 알고리즘을 “사용할 수 있다”고 설명한다. 따라서 팀이 채택할 수는 있지만, 교수님이 특정 알고리즘만 허용했다고 단정하지 않는다.

## 5쪽. 블록 생성 확률 테스트

### 교수님이 제시한 내용

- 최소 1,000회 이상 선택을 반복하는 단위 테스트를 구현한다.
- 설정된 확률과 ±5% 이내의 분포가 나타나는지 확인한다.
- 실제 게임의 생성 코드가 테스트를 통과해야 한다.

### 고객·평가자 관점

난이도에 따라 블록 등장 확률이 달라진다는 설명을 테스트 결과로 확인할 수 있어야 한다.

### 상세 요구사항

| ID | 요구사항 | 성격 | 상태 |
| --- | --- | --- | --- |
| R2-05-01 | 확률 검증 테스트는 최소 1,000회 선택을 수행해야 한다. | 검증 제약 | 원문 확정 |
| R2-05-02 | 테스트는 실제 게임의 블록 선택 기능을 호출해야 한다. | 검증 제약 | 원문 확정 |
| R2-05-03 | 블록별 관측 비율과 기대 확률의 차이가 ±5% 이내인지 확인해야 한다. | 검증 제약 | 오차 정의 확인 필요 |
| R2-05-04 | Easy·Normal·Hard 각각의 분포를 검증한다. | 검증 범위 | 도출 제안 |

### 반드시 확인할 오차 정의

기대 확률을 `p`, 관측 비율을 `q`라고 할 때:

| 해석 | 판정식 | 기대 확률 20%의 허용 범위 |  |  |
| --- | --- | --- | --- | --- |
| ±5퍼센트포인트 | ` | q − p | ≤ 0.05` | 15~25% |
| 상대 오차 ±5% | ` | q − p | / p ≤ 0.05` | 19~21% |

두 기준은 다르므로 답변 전까지 최종 합격 기준을 확정하지 않는다.

### 테스트 결과에 기록할 내용

- 난이도와 가중치
- 선택 횟수
- 블록별 기대 확률
- 실제 선택 횟수와 관측 비율
- 오차 계산 방식과 결과
- 재현에 필요한 난수 설정

반복 횟수 확대와 난수 시드 관리 방식은 테스트 설계 사항이다. 결과가 통과할 때까지 반복 실행하는 것을 합격 절차로 사용하지 않는다.

## 6쪽. 아이템 모드 추가

### 교수님이 제시한 내용

시작 메뉴에서 기존 게임과 아이템 모드를 선택할 수 있어야 한다. 스코어보드에서도 두 모드의 점수를 구분해야 한다.

### 사용자 요구사항

사용자는 시작 메뉴에서 플레이할 모드를 고르고, 기록을 확인할 때 어떤 모드에서 획득한 점수인지 알 수 있어야 한다.

### 상세 요구사항

| ID | 요구사항 | 출처 |
| --- | --- | --- |
| R2-06-01 | 시작 메뉴에서 일반 모드를 시작할 수 있어야 한다. | 원문 |
| R2-06-02 | 시작 메뉴에서 아이템 모드를 시작할 수 있어야 한다. | 원문 |
| R2-06-03 | 선택한 모드에 해당하는 게임 규칙을 적용해야 한다. | 원문 |
| R2-06-04 | 스코어보드에서 일반 모드와 아이템 모드의 기록을 구분할 수 있어야 한다. | 원문 |
| R2-06-05 | 일반 모드에서는 아이템 모드 전용 효과가 발생하지 않아야 한다. | 도출 |
| R2-06-06 | 기록에는 점수 획득 당시의 모드 정보가 유지되어야 한다. | 도출 |

### 검증 기준

- 각 메뉴에서 시작한 게임이 해당 모드로 실행되는지 확인한다.
- 일반 모드에서 아이템이 등장하지 않는지 확인한다.
- 두 모드의 기록을 저장한 뒤 식별 가능한지 확인한다.

### 팀 결정 사항

기록별 모드 표시, 필터, 탭, 별도 화면 중 어떤 방식으로 구분할지 결정한다. **화면 분리나 별도 순위표 자체는 이 페이지의 명시적 필수 조건이 아니다.**

기존 기록에 모드 정보가 없다면 이관·표시 방식을 별도로 정한다.

## 7쪽. 아이템 모드 게임 방식

### 교수님이 제시한 내용

- 10줄을 삭제할 때마다 아이템이 등장한다.
- 조건 달성 후 NEXT에 새롭게 나타나는 블록은 아이템이거나 아이템을 포함해야 한다.
- 아이템마다 서로 다른 문자를 사용한다.
- 지정된 2종 외에 자체 아이템을 최소 3종 추가한다.

### 사용자 요구사항

사용자는 줄 삭제를 통해 아이템을 얻고, NEXT를 보고 다음 아이템을 미리 식별할 수 있어야 한다.

### 상세 요구사항

| ID | 요구사항 | 출처·상태 |
| --- | --- | --- |
| R2-07-01 | 아이템 모드에서 10줄 삭제마다 아이템을 제공해야 한다. | 원문 |
| R2-07-02 | 지급 조건 달성 후 NEXT에 새로 나타나는 블록은 아이템이거나 아이템을 포함해야 한다. | 원문 |
| R2-07-03 | 아이템 종류마다 서로 다른 문자를 표시해야 한다. | 원문 |
| R2-07-04 | 지정 아이템 2종과 자체 아이템 최소 3종, 총 5종 이상을 제공해야 한다. | 원문 |
| R2-07-05 | NEXT에 예고한 아이템 종류는 해당 블록이 현재 블록이 되어도 유지되어야 한다. | 도출 |
| R2-07-06 | 누적 10·20·30줄 경계에 도달하거나 경계를 넘으면 지급 대상으로 처리한다. | 도출 제안 |

### 10줄 경계의 구체화 제안

**“10줄 초과”가 아니라 “10줄 도달 또는 초과”다.** 정확히 10줄이 되었을 때도 지급되어야 한다.

| 이전 누적 | 이번 삭제 | 이후 누적 | 제안하는 처리 |
| --- | --- | --- | --- |
| 8 | 1 | 9 | 지급 없음 |
| 9 | 1 | 10 | 지급 1회 |
| 9 | 4 | 13 | 지급 1회, 누적 13줄 유지 |
| 19 | 2 | 21 | 지급 1회, 누적 21줄 유지 |

누적 경계를 사용하는 방식과 초과분 유지 정책은 팀 규칙으로 명문화한다.

### 확인·결정 필요

- 아이템으로 삭제한 줄도 지급용 줄 수에 포함하는가?
- 기존 NEXT를 교체하는가, 다음에 새로 채우는 NEXT에 적용하는가?
- 한 번의 효과로 여러 10줄 경계를 넘으면 지급을 여러 회 예약하는가?
- 이미 아이템 지급이 예약되어 있다면 추가 지급을 어떻게 보관하는가?
- 아이템 종류별 등장 확률은 같은가?

원문의 “새롭게 나타나는 블록”을 기준으로는 기존 NEXT를 유지하고 새 NEXT에 적용하는 해석이 자연스럽지만, 평가 기준에 영향을 주므로 확인한다.

### 검증 기준

- 9→10, 9→13, 19→21 경계를 검증한다.
- 확정된 지급 시점에 NEXT에 아이템이 표시되는지 확인한다.
- NEXT와 실제 등장 아이템이 일치하는지 확인한다.
- 아이템이 5종 이상이며 식별 문자가 중복되지 않는지 확인한다.

## 8쪽. 줄 삭제 아이템

### 교수님이 제시한 내용

일반 블록 내부의 무작위 위치에 `L`을 표시한다. 블록이 더 이상 움직이지 못하면 `L`이 위치한 행을 삭제한다. 해당 행은 가득 차지 않아도 되며, 기존 방식으로 점수를 계산한다.

### 사용자 요구사항

사용자는 `L`의 위치를 보고 원하는 행에 배치해, 완성되지 않은 행도 삭제할 수 있어야 한다.

### 상세 요구사항

| ID | 요구사항 | 출처 |
| --- | --- | --- |
| R2-08-01 | 줄 삭제 아이템은 일반 블록 내부에 포함되어야 한다. | 원문 |
| R2-08-02 | 아이템을 문자 `L`로 표시해야 한다. | 원문 |
| R2-08-03 | 아이템 부착 위치는 블록이 실제로 차지하는 칸 중 무작위로 정해야 한다. | 원문 구체화 |
| R2-08-04 | 발동 조건에 도달하면 `L`이 있는 보드 행을 삭제해야 한다. | 원문 |
| R2-08-05 | 대상 행이 가득 차지 않았더라도 삭제해야 한다. | 원문 |
| R2-08-06 | 삭제한 줄에는 기존 점수 계산 규칙을 적용해야 한다. | 원문 |
| R2-08-07 | 블록 이동·회전 후에도 부착된 `L`의 위치를 일관되게 추적해야 한다. | 도출 |

### 발동 조건의 모호함

원문은 “더 이상 움직이지 못하게 되면”과 “바닥이나 다른 블록에 닿으면”을 함께 사용한다.

따라서 다음 중 어느 시점인지 정해야 한다.

- 아래 방향 이동이 처음 막힌 순간
- 기존 게임 규칙에 따라 블록 고정이 확정된 순간

고정 지연이 있는 게임에서는 두 시점이 다를 수 있다.

### 검증 기준

- 빈칸이 있는 행에 `L`을 놓아도 행이 삭제되는지 확인한다.
- 이동·회전 후 실제 `L`이 놓인 행이 삭제되는지 확인한다.
- 여러 생성에서 부착 위치가 고정되어 있지 않은지 확인한다.
- 삭제 행 수에 따른 기존 점수 계산이 적용되는지 확인한다.

### 확인·결정 필요

- 일반 완성 행과 `L` 대상 행이 겹치면 어떻게 계산하는가?
- 서로 다른 행이라면 같은 삭제 사건으로 묶어 다중 줄 점수를 적용하는가?
- 아이템 삭제가 속도 증가와 다음 아이템 지급에 포함되는가?
- 부착 위치는 균등 확률이어야 하는가? 원문은 무작위만 명시한다.

**팀 제안:** 같은 행이 두 조건에 해당해도 실제 삭제와 점수 계산은 한 번만 수행한다.

## 9쪽. 무게추 아이템

### 교수님이 제시한 내용

너비 4칸인 아이템이며 아래로 떨어지면서 밑의 블록을 제거한다. 처음에는 좌우로 움직일 수 있지만, 한 번 접촉하면 이후 좌우 이동은 불가능하다. 기본적으로 점수는 없지만 팀이 별도 규칙을 정할 수 있다.

### 사용자 요구사항

사용자는 접촉 전에 무게추의 위치를 정하고, 무게추가 아래 블록을 제거하며 내려가는 효과를 사용할 수 있어야 한다.

### 상세 요구사항

| ID | 요구사항 | 출처 |
| --- | --- | --- |
| R2-09-01 | 무게추의 너비는 4칸이어야 한다. | 원문 |
| R2-09-02 | 바닥이나 다른 블록에 최초 접촉하기 전에는 좌우 이동이 가능해야 한다. | 원문 |
| R2-09-03 | 최초 접촉 후에는 좌우 이동을 허용하지 않아야 한다. | 원문 |

| R2-09-06 | 기본 점수 정책에서는 사용과 블록 제거에 점수를 부여하지 않는다. | 원문 기본값, 변경 허용 |

### 상태별 동작

| 상태 | 좌우 이동 | 낙하·제거 |
| --- | --- | --- |
| 최초 접촉 전 | 허용 | 기존 낙하 방식에 따라 진행 |
| 최초 접촉 후 | 금지 | 아래 블록 제거를 계속 수행 |
| 바닥 도착 | 금지 | 종료 동작은 결정 필요 |

### 검증 기준

- 아이템 너비가 4칸인지 확인한다.
- 접촉 전과 후에 같은 좌우 입력을 주어 결과를 비교한다.
- 여러 층으로 쌓인 블록을 만나도 제거하며 내려가는지 확인한다.
- 합의한 점수 규칙이 적용되는지 확인한다.

### 확인·결정 필요

- 제거 범위는 실제 모양과 겹치는 칸인가, 폭 4칸 전체인가?
- 바닥에 도착한 무게추는 남는가, 사라지는가?
- 회전을 허용하는가? 허용한다면 너비 4칸 조건은 어떻게 유지하는가?
- 하드 드롭을 사용할 수 있는가?
- 제거된 개별 칸을 줄 삭제 수로 환산하는가?
- 사용자 정의 점수를 부여한다면 정확한 계산식은 무엇인가?

이 항목들은 원문에서 결정되지 않았으므로 구현 전에 규칙을 명시한다.

## 10쪽. 아이템 모드 관련 사항

### 교수님이 제시한 내용

아이템 추가가 어렵지 않도록 구조를 설계하고, 1차 요구사항과의 호환성을 유지해야 한다. 자체 아이템의 형태·기능 등을 문서화하여 평가팀에 제공해야 한다.

### 사용자·평가자 요구사항

- 평가자는 자체 아이템의 설명을 보고 실제 구현이 일치하는지 확인할 수 있어야 한다.

| R2-10-02 | 추가 게임 규칙은 1차 요구사항과 충돌하지 않아야 한다. | 호환성 | 원문 |

### 검증 가능한 조건으로 보완하기

“추가하기 쉽다”는 표현만으로는 판단하기 어렵다.

**팀 제안:** 새 아이템을 추가하는 예제를 통해 기존 아이템 동작을 수정할 필요가 있는지 검토하고, 기존 아이템 테스트가 유지되는지 확인한다. 구체적인 합격 기준은 팀이 합의한다.

### 자체 아이템 명세에 포함할 항목

- 이름·고유 문자·형태
- 등장 조건과 NEXT 표시
- 발동 조건과 효과 범위
- 지속 시간 또는 종료 조건
- 점수와 삭제 줄 수 집계
- 다른 아이템과의 중첩·우선순위
- 일시정지·게임 오버·재시작 시 처리
- 정상·경계·예외 상황별 기대 결과

### 1차 요구사항 대조 필요

문서는 아이템 표시와 색맹 모드, 난이도 설정 저장, 실행 환경을 예로 든다. 구체적인 저장 항목·재실행 복원·지원 환경은 1차 명세와 함께 확인한다.

특정 인터페이스나 `ItemFactory` 같은 클래스 이름은 **설계안**이며, 교수님의 필수 요구사항으로 기록하지 않는다.

| R2-12-03 | 명시된 기능을 충족하기 위해 필요한 암시적 조건도 검토해야 한다. | 완전성 | 원문 |
| R2-12-04 | 중간 평가에서 Line Coverage 50% 이상을 충족해야 한다. | 검증 제약 | 원문 |
| R2-12-05 | 기말 평가에서 Line Coverage 70% 이상을 충족해야 한다. | 검증 제약 | 원문 |

### 확인 필요

- 커버리지 측정 대상은 전체 코드인가, 특정 패키지인가?
- GUI·생성 코드 등의 제외 범위가 있는가?
- 지정된 측정 도구와 보고서 형식이 있는가?

분모와 제외 범위를 임의로 변경해 기준을 만족한 것으로 처리하지 않는다. 커버리지 수치와 요구사항 충족 여부도 별도로 확인한다.

### 강의자료 기준 최종 검토

| 검토 기준 | 이 프로젝트에서 확인할 질문 |
| --- | --- |
| 타당성 | 교수님과 사용자가 요구한 동작을 제공하는가? |
| 일관성 | 1차·2차 명세와 팀 추가 규칙 사이에 충돌이 없는가? |
| 완전성 | 입력·발동·종료·예외 조건이 빠지지 않았는가? |
| 실현 가능성 | 일정과 기술 범위 안에서 구현·검증할 수 있는가? |
| 검증 가능성 | 각 요구사항의 합격 여부를 관찰하거나 측정할 수 있는가? |

## 부록 A. 핵심 사용자 시나리오

### 시나리오: 10줄 달성 후 아이템 받기

| 항목 | 내용 |
| --- | --- |
| 관련 요구사항 | R2-07-01, R2-07-02, R2-07-05, R2-07-06 |
| 시작 상태 | 아이템 모드 진행 중, 누적 삭제 9줄 |
| 사용자 행동 | 현재 블록으로 1줄을 완성 |
| 정상 흐름 | 줄 삭제 → 누적 10줄 → 아이템 지급 대상 결정 → 새 NEXT에 아이템 표시 |
| 완료 상태 | 사용자가 다음 아이템을 식별할 수 있고, 실제 등장 시 동일한 아이템을 받음 |
| 경계 상황 | 9줄에서 4줄을 삭제해 13줄이 되는 경우 |
| 동시 활동 | 점수 갱신, 속도 변화, 삭제 애니메이션 |
| 미결정 영향 | NEXT 교체 시점과 아이템 삭제 집계 정책 확정 필요 |

이 형식으로 난이도 선택, `L` 발동, 무게추 최초 접촉, 게임 재시작 시나리오도 작성한다.

## 부록 B. 랜덤 벌칙 아이템의 위치

암전 `B`, 조작 반전 `R`, 회전 잠금 `K`는 현재 **팀 추가 요구사항 초안**으로 관리한다.

| 항목 | 분류·상태 |
| --- | --- |
| 벌칙을 NEXT에서 미리 표시 | 사용자 요청에 따른 팀 추가 요구 |
| 벌칙 중첩 금지 | 사용자 요청에 따른 팀 추가 요구 |
| 벌칙 블록 고정 후 발동 | 현재 설계 초안 |
| 등장 확률 3% | 밸런스 제안값 |
| 암전 3초·반전 5초·회전 잠금 1블록 | 효과별 제안값 |
| 예약·낙하·효과 적용 중 추가 추첨 금지 | 중첩 금지의 상세화 |
| 10줄 지급 아이템과 별도 추첨 | 팀 추가 규칙 |

**랜덤 벌칙 3종을 자체 아이템 최소 3종에 포함할 수 있는지는 교수님 확인이 필요하다.** 인정 여부가 확정되기 전에는 이 세 가지로 필수 아이템 수를 충족했다고 표시하지 않는다.

## 부록 C. Notion 관리 구조

페이지별 분석은 원문을 따라 읽는 용도로 유지하고, 실제 작업 관리는 요구사항 데이터베이스로 연결한다.

| 속성 | 예시 |
| --- | --- |
| 요구사항 ID | R2-08-05 |
| 제목 | 미완성 행의 강제 삭제 |
| 출처 페이지 | 2차 명세 8쪽 |
| 출처 구분 | 원문 / 도출 / 팀 추가 |
| 성격 | 기능 / 비기능 / 프로세스·검증 |
| 사용자 요구사항 | 사용자는 완성되지 않은 행도 아이템으로 삭제할 수 있다. |
| 시스템 요구사항 | 발동 시 `L`이 있는 행은 빈칸 유무와 관계없이 삭제되어야 한다. |
| 결정 상태 | 확정 / 제안 / 확인 필요 |
| 구현 상태 | 미착수 / 진행 / 구현 완료 |
| 검증 상태 | 미실행 / 통과 / 실패 |
| 검증 기준 | 빈칸이 있는 대상 행 삭제, 다른 행의 처리 확인 |
| 관련 이슈·PR | 구현 및 검증 이력 |
| 의존 요구사항 | 발동 시점, 점수 계산, 줄 수 집계 |
| 결정 근거 | e-class 답변 또는 팀 합의 기록 |

**결정 상태·구현 상태·검증 상태는 따로 관리한다.** 구현이 끝났더라도 요구사항 해석이 미확정이거나 검증하지 않았다면 완료로 뭉뚱그리지 않는다.
