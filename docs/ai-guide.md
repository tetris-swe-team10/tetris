# AI와 함께 개발하는 운영 지침

> 상태: 사용자 요청으로 정리한 운영 지침 · 정리일: 2026-11-09 · 팀 전체의 새 합의가 필요한 항목은 결정 기록으로 관리

## 1. 작업 시작

1. 사용자의 목표와 범위를 확인한다. 명확한 요청은 바로 진행하고 이미 허용한 일을 다시 승인받지 않는다.
2. `git branch --show-current`, `git status --short`와 현재 작업의 변경 내용을 확인한다.
3. [프로젝트 개요](project-overview.md), 관련 기능 명세, [열린 질문](coordination/questions.md)과 [작업 현황](coordination/status.md) 중 해당 부분만 읽는다. 노션 원문 전체를 매번 읽지 않는다.
4. 이슈·PR이 주어졌으면 현재 HEAD와 base, 기존 댓글을 먼저 확인한다. 다른 사람의 미커밋 변경을 테스트나 커밋에 섞지 않는다.
5. 최신 원격 확인이 필요하면 fetch한다. dirty 작업 트리에서 자동 pull·stash·reset하지 않는다. 네트워크 접근이 실패하면 확인한 로컬 기준과 미확인 범위를 알린다.

문서의 과거 날짜나 체크박스만으로 현재 완료를 판단하지 않는다. 실제로 읽지 않은 자료나 실행하지 않은 테스트를 확인했다고 쓰지 않는다.

## 2. 요구사항과 작업 배정

일반 흐름은 `요구사항 → Issue → 작업 브랜치 → 구현·관련 검증 → PR → 동료 리뷰 → 수정·답글 → 병합 → 현황 갱신`이다.

- 기능·버그별 이슈에 목적, 담당자, 요구사항 ID/출처, 완료 조건과 검증 방법을 적는다. 같은 이슈가 있으면 재사용한다.
- 하나의 사용자 스토리를 책임질 사람을 먼저 배정하고 그 안에 구현·검증 작업을 적는다. 모든 팀원이 한 스토리의 작은 작업만 나누어 맡은 것을 전체 스토리별 배정으로 설명하지 않는다. 이는 앞선 Agile Planning에 대한 수업 피드백을 반영한 운영 방식이다.
- 본문 작성자는 자동 담당자가 아니다. 팀원 배정은 실제 합의나 이슈 assignee에 근거한다.
- `결정 상태(확정/제안/확인 필요)`, `구현 상태`, `검증 상태`를 별도로 적는다.
- 교수님 원문에 없는 수치·아이템·점수 규칙은 팀 결정임을 표시한다. 해석이 평가를 좌우하면 e-class 확인 사항으로 남긴다.

GitHub에 글을 등록하는 것은 사용자가 요청했거나 작업 범위로 허용된 때 진행한다. 문서 초안 작성만 요청했다면 외부 등록까지 했다고 주장하지 않는다.

## 3. 브랜치와 커밋

| 변경 | 브랜치 예 | 커밋 예 |
| --- | --- | --- |
| 기능 | `feature/ghost-block` | `feat: 고스트 블록 표시 추가` |
| 버그 | `fix/settings-save` | `fix: 설정 저장 실패 시 상태 보존` |
| 문서 | `docs/project-guidelines` | `docs: AI 작업 지침과 평가 근거 정리` |
| 테스트 보강 | `test/ghost-visibility` | `test: 암전과 상태별 숨김 조건 독립 검증` |

앞의 세 접두사와 `feat/fix/docs/refactor/test/chore` 커밋 종류는 노션 「개발 운영 방식」을 따른다. `test/`는 테스트만 다루는 작업의 제안 관례이며 팀이 다른 관례를 정하면 그 결정을 따른다. `codex/` 접두사는 사용하지 않는다.

- 새 작업은 최신 main 기준을 우선하되 사용자가 현재 브랜치 수정을 요청하면 그대로 따른다.
- 선행 기능 브랜치 위에서 시작해야 하면 의존 PR과 기준 커밋을 본문에 표시한다. 선행 병합 후 base와 diff를 다시 확인한다.
- 한 커밋은 설명 가능한 변경 단위로 만든다. 빌드가 깨지는 인위적인 기능/테스트 분리를 만들지 않는다.
- 변경 파일을 명시해서 stage한다. `git add .`로 개인 설정·캐시·다른 사람의 작업을 함께 올리지 않는다.
- 커밋 전에 대상 diff와 `git diff --check`를 확인한다. merge·rebase·강제 push는 현재 승인 범위와 공유 브랜치 영향을 판단한다.

## 4. 구현 경계

- Model: `GameEngine`, `Board`, `Tetromino`, `GameConfig`, 아이템과 점수·생성 정책. JavaFX 화면 객체를 도메인에 넣지 않는다.
- Controller: `GameController`는 입력 명령·시간 진행, `AppController`는 화면 전환·앱 조립을 담당한다.
- View: `GameView`와 화면 클래스는 스냅샷과 상태를 표시한다. 화면에서 별도 점수 원장을 만들지 않는다.
- 상태 `PLAYING/ITEM_EFFECT/CLEARING/PAUSED/GAME_OVER`의 입력·시간 진행·복귀를 함께 고려한다.
- 공통 스냅샷, 보드 압축, 아이템 생명주기, 설정·기록 파일 형식의 변경은 연동 영향과 호환성을 적는다.
- 기본 블록 생성은 `WeightedPieceGenerator`, 점수는 `ScoringPolicy`, 아이템 지급은 `ItemAssigner` 경계를 재사용한다.
- Java 이름은 클래스 UpperCamelCase, 메서드·필드 lowerCamelCase, 상수 UPPER_SNAKE_CASE를 기본으로 한다. 기존 파일 스타일을 유지하고 무관한 전체 포맷 변경을 섞지 않는다.

## 5. 관련 테스트만 실행

사용자의 시간·토큰 절약 요청에 따라 기본값은 선별 검증이다. [품질·평가 관리](quality-and-evaluation.md)의 기능별 명령과 증빙 규칙을 따른다.

- 변경한 정상 경로뿐 아니라 직접 영향을 받는 경계·오류·상태 전이를 고른다.
- 작은 문서 수정은 링크·원문 보존·명령/경로 검사로 끝낸다. 게임 테스트를 일괄 실행하지 않는다.
- 테스트가 구현을 그대로 따라 쓰는지 확인한다. 다른 조건에서 먼저 반환해 실제 검증하려던 분기가 실행되지 않는 테스트를 피한다.
- 의심만으로 오류를 단정하지 않는다. 추가 재현 검증을 했다면 기존 제품 테스트와 검증 목적을 구분한다.
- 전체 실행이 필요해진 이유가 없으면 이미 통과한 검증을 반복하지 않는다.

## 6. PR와 코드 리뷰

PR에는 문제와 바뀐 동작, 이슈 연결, 실제 실행 명령·결과·미실행 범위, 경계/위험, 관련 명세를 적는다. 화면 변경이면 해당 상태의 화면 또는 재현 방법을 포함한다. [.github 템플릿](../.github/PULL_REQUEST_TEMPLATE.md)을 사용한다.

- 리뷰는 현재 HEAD의 diff와 호출 경로를 확인하고 기존 지적을 중복 등록하지 않는다.
- 코멘트에는 파일·줄, 발생 조건, 실제 영향, 수정 방향을 쓴다. 현재 동작 문제와 비차단 테스트 제안을 구분한다.
- P1은 빌드/핵심 동작을 막는 높은 우선순위, P2는 수정할 일반 동작 문제, P3는 비차단 보강 제안을 뜻하는 팀 내 표기다. 심각도를 과장하지 않는다.
- 형식 맞추기용 칭찬·억지 문제·미실행 테스트 통과 주장을 남기지 않는다. 문제를 못 찾았다면 검토 범위와 함께 그대로 말한다.
- 작성자 자신의 점검은 **작성자 자체 점검**으로 표시한다. AI 도구나 계정을 바꿔도 독립된 동료 리뷰가 되지 않는다.
- 지적에 동의하면 같은 브랜치에서 수정하고 관련 테스트 후 커밋을 push해 기존 PR에 반영한다. 답글에 커밋과 검증 범위를 남긴다. 동의하지 않으면 근거를 설명한다.
- 이미 병합된 PR의 리뷰는 **병합 후 사후 리뷰**로 적는다. 이전 문제의 후속 해결 PR도 표시하며 병합 전 리뷰로 소급하지 않는다.
- 사용자가 병합을 요청한 때 대상 PR·base·HEAD·의존 관계를 확인한다. 충돌 해결로 구현이 달라지면 직접 영향받는 기능을 다시 검증한다.

## 7. 작업 종료와 인수인계

완료한 변경·다음 작업·막힌 점을 [작업 현황](coordination/status.md)에 짧게 남긴다. 새 합의는 [결정 기록](coordination/decisions.md), 열린 문제는 [질문 목록](coordination/questions.md)에 출처와 상태를 기록한다.

사용자에게 변경 요약, 실제 검증 범위, 현재 브랜치, 커밋/PR/병합 여부를 사실대로 알린다. 지침서 작성, 이슈 등록, PR 생성, 병합, 릴리스 업로드는 서로 다른 완료 단계다.
